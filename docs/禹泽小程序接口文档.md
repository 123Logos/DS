# 禹泽小程序接口文档

> 业务基准：《禹泽数字科技小程序会员消费增值与六星店长白酒专卖需求文档》V1.1，2026-10-16，待甲方评审。编制：2026-10-18。
>
> **当前源码接口、需求缺口、未实现的目标契约分开描述。** 示例是虚构的结构示例，不是实测响应。本文现状表为静态核对；文档作者未启动项目或运行检查。主代理本轮WSL的48项回归通过与HTTP冒烟证据见[安全与测试报告](禹泽项目安全与测试报告.md)。不能据此认定部署已完成、所有资金链路已验收，或目标接口已经实现。

## 1. 总体约定

### 1.1 业务主旨

消费平台商品 → 积分 → 每日雨点 → 30 天优惠券。优惠券可兑换农场实物（不产生积分），或兑换咯哒蛋（80% 入底池、20% 入雨点补贴池）。达到约定的 100% 权益增值条件后自动转咯哒券，咯哒券仅兑换坛装白酒。六星店长可挂牌名下唯一合同编号酒坛；成交后转移权属并结算。

**现有普通商品、普通优惠券、商户收款码和会员六星字段不能当成这套业务已实现。** 当前未找到咯哒蛋、咯哒券、合同酒坛、挂牌市场或对应账本路由/schema/service。

### 1.2 地址、认证、类型

- 下文完整地址写为 `{{BASE_URL}}/实际路径`；`BASE_URL` 是运维给出的 HTTPS 服务域名，不包含 `/api`。项目路径并不统一：`/user`、`/order` 无 `/api`，商品是 `/api/products`。
- JSON 写请求：`Content-Type: application/json`；响应通常 `application/json`。GET 无请求体。示例默认 `Accept: application/json`。
- 标记 **Bearer** 的接口必须传 `Authorization: Bearer <业务登录token>`；不是微信服务端 `access_token`。JWT、启用时的 UUID、124 字符微信登录 token 由 `core/auth.py` 处理。失效通常 401，冻结/注销 403；缺失认证头可由 HTTPBearer 返回 401/403（依赖版本）。
- 标记 **未校验登录** 是安全缺口，不代表可上线向公众开放。调用时自行传 Bearer 不能补上服务端权限校验；应在权限修复后上线。
- 会员状态：`0` 正常、`1` 冻结、`2` 注销。`member_level` 是 0–6；`unilevel` 是另一套联创等级，不等于六星店长权限。
- 现有金额通常 JSON number、单位元；微信 `total_fee` 和永久码下单 `amount` 为整数分。积分和雨点是权益数量，不要标成人民币。当前 `POINTS_DISCOUNT_RATE=1.0`，只是现有代码的积分抵扣配置，不是 Q1/Q2/Q3 的确认值。
- SQL Decimal 经自定义响应转为 number；部分财务接口特意返回 string。时间有 ISO 日期时间与 `YYYY-MM-DD HH:mm:ss` 两类；日期为 `YYYY-MM-DD`。源码未统一时区契约，联调需确认部署时区，不擅自添加 `Z`。
- 无统一成功包络：用户/订单直接对象或数组；商品 `{status,data,...}`；财务 `{success,message,data}`；线下 `{code,message,data}`。不得统一假定 `response.data.data`。
- 未写出的长度/上下限表示源码未限制，不是无限输入获得授权。前端不应以输入校验代替后端约束。
- 除明确说明的订单键外，现有接口没有通用 `Idempotency-Key` 协议；无明确限流的接口不能宣称有每分钟额度。

### 1.3 通用错误与分页

| HTTP | 当前错误结构/条件 | 前端处理 |
|---|---|---|
| 400 | `{"detail":"优惠券不在有效期内"}`；业务条件不满足 | 展示可理解原因，刷新余额/订单，不盲重试写操作 |
| 401/403 | `{"detail":"认证令牌无效或已过期"}` / 冻结、注销或无权操作 | 重新登录或停止操作 |
| 404 | `{"detail":"订单不存在"}` 等 | 返回列表，不伪造空订单 |
| 409 | 支付参数与微信首单不一致、券已用等 | 查询原订单，再重新决策 |
| 422 | `{"detail":[{"type":"missing","loc":["body","user_id"],"msg":"Field required","input":{}}]}`，也可能 detail 为业务字符串 | 定位字段；不能假定 detail 永远 string |
| 429 | 订单创建中的用户锁冲突 | 禁用重复提交，等待原请求结果 |
| 500/502/503 | `{"detail":"服务器内部错误，请稍后重试"}`，5xx 经全局处理隐藏内部细节 | 保留 `X-Request-ID` 排查；资金操作先查状态 |

通用错误无稳定业务 code；不得把中文 message 当长期业务枚举。分页按各接口的 `rows` / `coupons` / `data` 读取，**当前没有统一 `items` 或 `has_more`**。有 total 时前端可计算 `page * page_size < total`（使用该接口实际 size 字段）；空列表示例见下。成功默认 HTTP 200。

## 3. 会员登录、个人中心与权益查询（当前接口）

### 3.1 微信小程序登录

**基本信息**：`POST {{BASE_URL}}/wechat/login`，无需登录，JSON，200。请求由原始JSON读取；本次增加昵称长度/空白校验及新用户注册前的微信内容审核。

| body字段 | 类型/必填/默认 | 规则和含义 | 合法/非法 |
|---|---|---|---|
| code | string，必填，无 | `wx.login` 临时码，服务端向微信换 openid | `<wx-login-code>` / 空字符串 |
| nickName | string，必填，无 | 1–100字符且非空白；新用户使用code换得的openid审核通过后才创建，存量登录不修改昵称 | `测试会员` / 空白或超过100字符 |

```http
POST {{BASE_URL}}/wechat/login
Content-Type: application/json

{"code":"<wx-login-code>","nickName":"测试会员"}
```

成功示例：`{"uid":101,"token":"<业务token>","level":0,"is_new":true,"openid":"<本用户openid>","unionid":""}`。

| 返回字段 | 类型/必返/空值 | 含义 |
|---|---|---|
| uid | integer，是 | 平台用户 ID，例如101 |
| token | string，是 | 业务认证令牌，微信路径生成124字符；不得记录日志或硬编码 |
| level | integer，是 | 0–6会员等级 |
| is_new | boolean，是 | 是否本次注册 |
| openid | string，是 | 此小程序用户标识，不是认证凭据 |
| unionid | string，是，未获得时空串 | 微信开放平台标识 |

**使用与错误**：先 `wx.login`，再本接口，保存业务 token。不要重复使用临时 code；接口不承诺重复调用返回相同 token。非法 JSON、非对象、缺 code/nickName、昵称空白/超长为400；新用户昵称审核review/risky为400、审核服务异常503；其他微信/内部失败可500。存量账号登录不写昵称，因此不对传入昵称执行写入审核。响应**不含 session_key**。本接口不能视为手机号绑定或实名完成。

### 3.2 手机号密码登录/自动注册

`POST {{BASE_URL}}/user/auth`，无需登录，JSON，200。

| body字段 | 类型/必填/默认/校验 | 含义/示例 |
|---|---|---|
| mobile | string/是/无；schema无手机号正则 | 手机号，如`13800000000` |
| password | string/是/无；schema无最小长度 | 用户密码，仅通过HTTPS传递 |
| name | string或null/否/null | **新用户必须省略或null**；非null拒绝400，防止绕过昵称审核；存量登录不修改昵称 |

请求 Headers 同3.1；Body：`{"mobile":"13800000000","password":"<用户输入密码>"}`。非法：缺 password →422；新用户传`"name":"测试会员"`→400。注册默认昵称沿用原服务，后续通过受保护资料接口审核设置。

响应：`{"uid":101,"token":"<业务token>","level":0,"is_new":false}`；字段同3.1，**无 openid/unionid**。旧用户密码错误400，冻结/注销403，新用户注册业务错误400。该路径代码指定 UUID token，若部署禁用 UUID，后续 Bearer 接口可能拒绝；小程序优先微信登录。不会通过此接口自动获得微信 openid；不能用手机号拼出 openid。

### 3.3 用户详情、积分余额

**基本信息**：`GET {{BASE_URL}}/user/info?mobile=13800000000` 和 `GET {{BASE_URL}}/points/balance?mobile=13800000000`。当前均未校验登录，无请求体；只读，可重复查询。query `mobile` 为必填 string，无默认及格式约束。非法缺失 →422。Headers：`Accept: application/json`，建议携带业务 Bearer，但现有实现不使用它限制资源。

`/user/info` 成功：

```json
{"uid":101,"mobile":"13800000000","name":"测试会员","avatar_path":null,"member_level":2,"is_merchant":0,"status":0,"referral_code":null,"direct_count":0,"team_total":0,"assets":{"member_points":100,"merchant_points":0,"withdrawable_balance":0},"referrer":null}
```

| 返回字段 | 类型、空值、含义（均必返） |
|---|---|
| uid、mobile | integer、string；用户ID/手机号 |
| name、avatar_path、referral_code | string或null；昵称/头像路径/推荐码，null=未设置 |
| member_level | integer；会员0–6星，不代表酒坛权限 |
| is_merchant | integer；0普通、1商户、2平台/第三方 |
| status | integer；0正常/1冻结/2注销，详情排除注销用户 |
| direct_count、team_total | integer；直推数/最多6层团队人数 |
| assets.member_points | number；会员消费积分 |
| assets.merchant_points | number；商家积分，不是六星卖家20%规则的证明 |
| assets.withdrawable_balance | number；旧提现余额元，不是咯哒券余额 |
| referrer | object或null；无推荐人为null |
| referrer.mobile、referrer.name、referrer.member_level | string、string或null、integer；推荐人手机号/昵称/等级 |

`/points/balance` 直接返回 `{"member_points":100,"merchant_points":0,"withdrawable_balance":0}`，含义同上，无 assets 外层；动态旧表字段可能补0。详情用户不存在或注销404；余额用户不存在400。查询无幂等键或明确限流。**缺资源归属鉴权，不能直接作为生产私密资产接口开放。**

### 3.4 雨点汇总

`GET {{BASE_URL}}/points/summary?user_id=101`，当前未校验登录，无请求体，200。query `user_id: integer` 必填且 >0，无默认；`0` 非法422。

响应：

```json
{"unilevel_points":10,"subsidy_points":20,"team_reward_points":5,"referral_points":5,"cumulative_total":40,"remaining_points":30,"used_points":10}
```

所有字段必返 number：`unilevel_points` 联创累计（库字段 points）、`subsidy_points` 日/旧周补贴累计、`team_reward_points` 团队累计、`referral_points` 推荐累计、`cumulative_total` 四项之和、`remaining_points` 库 `true_total_points`（当前可用雨点）、`used_points` 前两者相减。用户不存在404。由于商品直接赠送雨点也写入 true_total_points，但不计入四项累计，**used_points可能为负，不能当作可靠的新权益消耗总账**。此接口没有每日结算明细，也没有蛋/咯哒券字段。

### 3.5 积分流水

`GET {{BASE_URL}}/points/log?mobile=13800000000&points_type=member&page=1&size=10`，当前未校验登录，无请求体，200。

| query字段 | 类型/必填/默认 | 约束/意义 |
|---|---|---|
| mobile | string/是/无 | 用户手机号 |
| points_type | string/否/member | 实际按数据库 type 精确筛选，schema未限制；已知 member/merchant/company |
| page | integer/否/1 | 页码，源码未限制下界，客户端只传≥1 |
| size | integer/否/10 | 每页数，源码未限制上限 |

非法：`page=abc` →422；不要依赖`page=0`得到规范错误。成功结构：

```json
{"rows":[{"id":1,"user_id":101,"change_amount":10,"balance_after":100,"type":"member","reason":"购买普通商品获得积分","related_order":5001,"created_at":"2026-10-18T10:00:00"}],"total":1,"page":1,"size":10}
```

`rows[]`：id流水ID、user_id用户ID、change_amount带符号增减数量、balance_after变动后余额（均number，ID为integer）；type权益类别string；reason说明string/null；related_order订单内部ID integer/null（无订单关联为空）；created_at时间string。返回实际表列，升级库可追加字段，客户端应忽略未知字段。`total/page/size` integer必返；无has_more。空：`{"rows":[],"total":0,"page":1,"size":10}`。用户不存在400，数据库异常500。只读无副作用，不满足Q17永久保存承诺。

### 3.6 我的普通优惠券

`GET {{BASE_URL}}/my?user_id=101&status=all&page=1&page_size=20`，当前未校验登录，无请求体，200。路径是根 `/my`，不是 `/user/my`。

| query字段 | 类型/必填/默认 | 校验/含义 |
|---|---|---|
| user_id | integer/是/无 | 要查询的用户；未做登录归属绑定 |
| status | string/否/all | all不筛选，unused/used/expired；未设枚举校验 |
| page | integer/否/1 | 未设下界 |
| page_size | integer/否/20 | 1–99999 |

非法 `page_size=0` →422。返回：

```json
{"coupons":[{"id":10,"coupon_type":"user","amount":1,"status":"unused","valid_from":"2026-10-18","valid_to":"2026-11-17","used_at":null,"created_at":"2026-10-18T00:05:00"}],"total":1,"page":1,"page_size":20}
```

`coupons[]`各字段必返：id integer券记录ID；coupon_type string user会员/merchant商家；amount number旧券面额元（不是张数、不是咯哒券）；status string unused未用/used已用/expired过期；valid_from/valid_to string日期；used_at string/null未使用为空；created_at string发放时间。此接口**不返回 applicable_product_type、order_no、统计汇总**，即使某schema定义过也不能假设存在。total/page/page_size整数。空：`{"coupons":[],"total":0,"page":1,"page_size":20}`。

`expired`筛选包含“数据库unused但日期已过”的记录，该记录返回status仍可能是unused；`unused`筛选仅查状态，不能保证日期有效。消费前必须由服务端再次校验。只读，无固定频率承诺。

### 3.7 即将过期券与可用券

| 地址 | 认证 | query | 成功包络 |
|---|---|---|---|
| `GET {{BASE_URL}}/api/coupons/expiring?days=3` | Bearer当前用户 | days integer可选默认3，1–30 | `{success:true,message:string,data:{expiring_coupons:[],days:3,total:0}}` |
| `GET {{BASE_URL}}/api/offline/coupons?amount=10000` | Bearer当前用户 | amount integer可选默认不传，>0，单位分 | `{code:0,message:"查询成功",data:[]}` |

请求均无请求体；Headers `Authorization: Bearer <token>`、`Accept: application/json`。非法 `days=0` / `amount=0` →422。

到期接口 `data.expiring_coupons[]`：id integer、coupon_type string、amount number元、applicable_product_type string（all/normal_only/member_only）、valid_from/valid_to string日期、created_at string日期时间，均必返，**没有status/used_at**。days/total整数。只取unused且到期日在今天至今天+days（包含端点），按到期日升序。

线下接口 `data[]` 包含3.6券字段并增加 `applicable_product_type`、`applicable_product_type_text`（不限制/仅普通商品/仅会员商品，未知时“未知”）。例如：

```json

**契约缺陷**：`list_available`实际忽略amount，只查询status=unused，没有过滤有效日期和门槛；“可用”是接口命名而非完整可用性保证。服务异常500，认证错误按1.3。读操作可重试。

### 3.8 资料修改与文本审核变更

`POST {{BASE_URL}}/user/update-profile` 已由主代理完成安全调整：必须 Bearer 登录，body.mobile 必须对应登录用户；name如提供必须1–100字符且非空白，经微信 scene=1 服务端审核，仅明确通过才保存，审核不通过400、服务异常503。旧客户端必须新增 Authorization，不能仅传手机号。请求结构沿用 `UpdateProfileReq`：mobile必填string；name、old_password、new_password可选string/null；avatar_path虽然schema存在，但非null直接400，头像必须走专用上传审核接口。密码修改须提供旧密码；详情请结合本次代码变更记录，不可绕过审核直接写库。

安全代理的完整参数、返回及测试说明见 [msgSecCheck 专项文档](api/msg-sec-check.md)。主文档只固定安全基线：**微信v2返回明确pass才放行；超时/网络/微信错误/未知结构一律false；openid必须绑定当前登录用户，不信任前端任意openid。** 仅调用代理但未在写入处强制审核，不构成内容安全闭环。

## 4. 当前结算政策与六星含义

### 4.1 已存在的旧算法，不是 V1.1 参数批准

- 日任务00:00：补贴池余额×日比例（代码默认0.05），除以会员积分+商户积分+公司积分总额；积分值上限0.005，手工值作为更低上限。给会员增加 subsidy_points/true_total_points，同时扣除等额 member_points。Q1未确认，不能沿用为新需求算法。
- 月初1日00:05：余额>330时转余额减330；余额0–330时转min(余额,30)，生成一张对应面额券，扣雨点；有效期该月首日至月末。用户/月唯一结算记录用于防重复。
- **实际月结筛选 `users.status=1`，但全局1=冻结、0=正常。** 旧文档写“正常会员”与实现不一致，影响正常会员拿券，必须单独修复和验收。
- 每日23:58：处理valid_to早于今天且unused的券；普通券入subsidy_pool，带rain_settlement_id的月结券入director_pool，用户member_points加等面额。状态条件更新防止重复记账。
- 手工发券还有每张1元、扣1雨点的旧接口；这些都不是Q2/Q3的书面结论。月结30不是30天，330不是V1.1门槛。

### 4.2 现有六星相关能力

会员商品结算按购买件数 `min(旧等级+数量,6)` 升星；此外存在直接调星接口。并未实现Q8所需的六星店长业务资格/降级规则。

### 5.5 确认收货与退款

`POST {{BASE_URL}}/order/confirm-receive`，JSON `{"order_number":"<订单号>"}`；order_number必填string，无默认/长度约束；当前无登录依赖，route未向service传用户ID，存在越权风险。成功 `{"ok":true,"message":"确认收货成功"}`（boolean/string必返）；仅pending_recv→completed，订单不存在/状态不符400；重复确认不是成功回放。缺订单号422。只更新本地，不主动同步微信，也不再发积分。

`POST {{BASE_URL}}/refund/apply`，当前无登录依赖，JSON：`{"order_number":"<订单号>","refund_type":"refund_only","reason_code":"申请退款"}`。三字段均必填string；refund_type数据库支持return退货退款/refund_only仅退款，但schema未设枚举；reason_code实际存reason文本。成功 `{"ok":true}`；重复已申请400；缺字段422；非法refund_type可能到数据库才500，不保证422。未形成V1.1五类权益回退闭环。

`GET {{BASE_URL}}/refund/progress/<订单号>`，未校验登录，无请求体；返回退款记录或空对象`{}`。字段：id integer、order_number string、refund_type string、reason string、status string（applied/seller_ok/refund_success/rejected/seller_rejected）、reject_reason和merchant_address string/null、created_at/updated_at string。示例 `{"id":1,"order_number":"<订单号>","refund_type":"refund_only","reason":"申请退款","status":"applied","reject_reason":null,"merchant_address":null,"created_at":"2026-10-18T11:00:00","updated_at":"2026-10-18T11:00:00"}`。

存在 `/order/status` 任意新状态写入及 `/refund/audit` 等管理入口，但未建立完整鉴权与合法迁移校验，**不得让会员端用通用status接口模拟付款成功/取消/退款**。支付、退款、取消后的积分/雨点/券/蛋恢复以Q11审批后另行实现；普通退款成功不代表新权益已正确回退。

```

正额响应：

```json

```

返回必返：prepay_id string；pay_params object，其appId/timeStamp/nonceStr/package/signType/paySign都是string、分别为应用ID/秒时间戳/随机串/预付包/签名算法/签名；total_fee integer分，服务端最终应付；wechat_raw_response object为微信原始返回，成功通常含prepay_id，其他上游字段不稳定，**业务前端不要依赖它**。

**错误**：非法JSON/缺订单号、金额、openid/非正金额400；订单不存在404；非pending_pay400；积分余额不足400；券不属买家/过期400，券已用409，优惠券叠加超限400；微信参数冲突409、缺openid422、上游失败502，结构异常500。`/order/pay`旧代理广泛捕获异常可能将原4xx变500，不推荐。

**零元兼容缺陷**：本接口先要求total_fee>0，但后端重算≤0时返回直接六个支付字段，package=`prepay_id=ZERO_ORDER`，没有pay_params外层，且只是同步订单金额后返回，不完成真正微信支付。**不要将该标记交给微信，也不要据它宣布支付完成**；正确零元流程在创建订单need_pay=false时完成。订单正额转零额路径需后端修复后联调。

## 9. 算法与契约冲突清单

1. **需求内部兑换比例冲突**：3.1写“1优惠券=100枚”，但3.2/R4公式 `(券×80%)/实时值` 在初值0.01下是1券=80枚；3.4的100券=8000枚支持80枚口径。文档不能把100枚作为可执行兑换值，须甲方修订确认。
2. **总量/分母歧义**：1亿发行总量恒定不等于实时值分母必定固定1亿；3.2说“平台余额”，4.5说“流通蛋减少”，4.7又说总量不变。须区分总发行、平台库存、用户持有、回收/冻结数量，Q5/Q6解决。
3. **成本与100%基准**：100券只80券参与发蛋，100%增值是相对100券支出、80券入池还是兑换时价格？多次持仓合并如何判定“个人全部清零”？Q4不能只用前端`当前值/初始值`自算。
4. **兑换快照自影响**：先入底池会改变价格，先减平台库存也会改变分母；用交易前/后值结果不同。必须明确原子报价时点，前端预估不应充当最终账务值。
5. **月结与每日矛盾**：330/30/月初不是FR-203每日折算；月末有效不是30天；月结券进入director_pool不是雨点补贴池。旧policy文件不能覆盖V1.1。
6. **会员状态矛盾**：月结SQL选冻结用户status=1，旧说明却称正常会员；这是代码事实与状态枚举冲突，非待定业务政策。
7. **积分长期有效与日扣减**：当前日补贴扣member_points，V1.1未授权此消耗；Q1应明确是否消耗积分，而不是把旧行为直接认定正确。
8. **券兑换农场不发积分**：基础消费积分按现金发，零现金不发该部分，但商品reward_points/reward_rain额外奖励仍发，FR-204需独立控制。
9. **雨点累计不可闭合**：直接商品赠送进入true_total_points但不进入四渠道累计，可导致used_points负值，不能拿此汇总充当全量权益台账。
10. **币种/单位不统一**：普通券amount是元、管理发券amount是张数、线下amount是分、线上total_amount是元、支付total_fee是分；不能将普通券金额直接映射咯哒券数量。Q7/Q15未定。
11. **商户分账不是六星结算**：现有平台计提比例和多个资金池不是卖家80%现金+20%积分，director_pool也不是V1.1底池；不能只改字段名。
12. **已有幂等不可靠**：创建订单键命中返回类型不一致、键不带user_id、购物车一分钟拦截先发生；预支付与零元返回不统一。前端必须查单而非盲重试。
13. **身份与订单字段信任**：若干查询/修改只收mobile/user_id，立即购买信任price，支付信任openid；这些不能沿用于目标接口。
14. **地址/期限文案不符**：address_id在schema但创建不读取；订单DDL注释写7天而创建为12小时；API文档以执行代码为现状，需求未规定的时长不能偷渡到新白酒规则。
15. **酒坛交易与权益禁交易边界**：实物酒坛可以按需求交易；咯哒蛋/券不得公开交易、转赠、提现、场外变现。不能将“权益禁止交易”误做“白酒不可售卖”，也不能借白酒挂售提供权益变现入口；须法务审查Q14风险。

## 10. 缺失业务目标接口契约（设计建议，全部未实现、不可调用）

### 10.1 设计边界及统一结构

本章路径为**建议命名**，不在当前路由注册中，不能向现有服务请求验证是否成功。这里只确定可评审的接口形状和一致性要求，不批准Q1–Q17的业务值。沿用现有FastAPI/数据库/认证基础设施即可，无需为文档引入新框架；但现有鉴权缺口、宽松金额输入、普通券/雨点混合账不能原样复制。

建议新域独立版本前缀`/api/v1/rights`、`/api/v1/wine`、`/api/v1/admin`，不覆盖旧字段语义。所有个人接口从Bearer取用户，不接受user_id作为归属授权；后台需专门管理/财务角色。所有写入以服务端价格、持仓、角色、权属为准。

**拟定公共返回**：`{code:"OK",message:"成功",data:...,request_id:"..."}`。code/message/request_id都是必返string；data按各接口展开，不能使用任意object代替。错误`{code:"RULE_UNCONFIRMED",message:"业务规则待确认",data:null,request_id:"..."}`。HTTP建议：401未登录、403角色/归属失败、404资源不存在、409状态/版本/幂等冲突、422参数/余额/库存不足、503依赖不可用或业务规则未确认。业务code建议`INVALID_ARGUMENT`、`NOT_OWNER`、`INSUFFICIENT_BALANCE`、`POOL_INSUFFICIENT`、`QUOTE_STALE`、`LISTING_UNAVAILABLE`、`STATE_CONFLICT`、`IDEMPOTENCY_CONFLICT`、`RULE_UNCONFIRMED`。这些**不是现有错误码**。

权益数值建议十进制string，货币建议`*_fen: integer`。权益单位单列point/rain/coupon/egg/goda_coupon，严禁将权益数目当现金分。精度、最小量、舍入和尾差账户均待规则评审，不预设小数位。时间建议带偏移ISO8601，业务日边界及时区由评审明确。

分页建议query `cursor:string|null`、`page_size:integer`，返回`items:array`、`next_cursor:string|null`、`has_more:boolean`；page_size默认/上限在技术评审批准后配置，不在本文冒定业务额度。首次无cursor；空`{items:[],next_cursor:null,has_more:false}`。全量报表不以单页结果冒充总量。

资金/权益写接口建议必填header `Idempotency-Key:string`：用户+操作+键唯一，同键同请求返回同结果、不同参数409，事务提交后方可记录成功；有效保留周期须覆盖支付/回调/售后窗口，待Q11/Q17确认。重复微信通知以交易ID/业务事件ID唯一约束，同订单同结算版本只能发一次权益。客户端超时查询原操作；不能换键绕过库存锁。

### 10.5 自动转化与咯哒券兑酒（FR-206/207）

系统按Q4成本口径监测，达到阈值时单事务锁用户相关持仓与池快照、生成唯一conversion事件、清相应蛋持仓、发咯哒券、写台账；数量按 `蛋数量×触发时实时咯哒值`。Q4未定时不运行监测；Q5未定时不擅自返蛋到平台或销毁；多人同时转化必须按Q6统一顺序/快照策略，避免不同节点重复转化。

`POST /api/v1/wine/redemption-quotes`：Bearer，body listing_id string必填（或平台初始酒坛产品明确后使用独立来源字段，不能混同普通SKU）；data quote_id/listing_id/contract_no string、goda_coupon_quantity/pool_coupon_debit decimal string、wine_price_fen integer=300000（**仅酒价**）、fees对象（packaging_fen/container_fen/shipping_fen integer或null，null=未确认不是免费）、rule_version/expires_at string、blocked_questions数组。Q7/Q13未确认返回RULE_UNCONFIRMED，不写3000咯哒券作为默认值。

兑换提交统一走下节白酒订单，payment_method=goda_coupon。必须同事务扣本人咯哒券、按批准单位等额扣底池、转合同权属、卖家应付/积分和买家不发积分、写全量账；池不足拒绝，不能透支或只发酒不减池。无提现、转赠、兑换其他商品接口。

## 11. 合规、接入顺序与验收边界

### 11.1 强制文案与功能限制

权益页面统一展示：**“本权益为会员消费回馈福利，非金融资产，不可提现、不可转让”**。不得出现投资、理财、保本盈利、保收益、稳赚、数字货币/稳定币/代币或资产升值营销；100%仅在客观规则说明中展示，不宣传确定收益。禁止权益公开交易/转赠/场外变现入口。实物酒坛交易与权益兑换必须分域展示。所有页面、通知、推送及营销话术上线前合规审核，后端配置文案也不例外。

### 11.2 当前前端可遵循的接入顺序

1. 微信登录取得业务token和当前openid；不把session_key传到客户端。
2. 查商品/SKU、普通积分、普通券；承认现有查询鉴权缺口，生产接入前修复。
3. 只在旧商城已授权范围调用order/create；配送传custom_address，不能仅address_id；前端单价来自商品详情，后端信任价格缺陷需修复。

### 12.2 本次接口行为变更与客户端迁移

本文件是新编业务接口说明；目标契约不是上线承诺。主代理同时进行昵称/msgSecCheck安全修复，以下为其明确交付变更，最终测试结果见主代理报告：

| 接口 | 变更前 | 变更后/迁移 |
|---|---|---|
| `/api/security/msg-sec-check` | 安全检查行为存在放行问题 | 微信v2仅明确pass为true，其余false；openid绑定登录用户；字段及错误详见专项文档 |
| `/user/update-profile` | 仅mobile定位，昵称未强制安全审核 | 必须Bearer且mobile匹配本人；name如提供必须1–100字符且非空白，scene=1审核通过才保存；拒绝400、依赖异常503；旧客户端补Authorization，不得失败后回退旧写法 |
| `/wechat/login` | 非空nickName即可进入注册 | nickName必须1–100字符非空白；**新用户注册前**用code换得的openid审核昵称；review/risky400、服务异常503；存量用户登录不更新昵称，因而不对传入昵称执行写入审核 |
| `/user/auth` | 新注册可传name直接写昵称 | **新用户且name非null时400**；省略/null走原服务默认昵称，已有账号登录不改昵称；客户端注册时移除name，后续通过绑定微信身份的受保护资料接口设置昵称 |

这是安全收紧，属于旧匿名资料写入/自由昵称注册客户端的破坏性变更；不保留不安全兼容绕过路径。不得在小程序失败时调用另一路由逃避审核。所有503仍可能被全局错误处理替换为“服务器内部错误，请稍后重试”，前端按HTTP状态处理，不依赖具体文案。
