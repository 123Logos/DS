# 方案二：独立测试环境＋受控小额真实联调

日期：2026-10-24。结论：**有条件可行，适合长期维护；不应等整套环境建好才封堵现网风险。0.01 元是最后的外部集成样本，不是整套测试方法。**

## 1. 技术方案可行性评判

**用户提出的方案：**重新搭建测试环境，使用 0.01 元等小额度测试，避免影响线上用户。

**评判结果：**有条件可行。需要把应用/数据隔离和真实支付的外部副作用分开管理。

| 维度 | 分析 |
| --- | --- |
| 技术可行性 | 当前 FastAPI、PyMySQL、MySQL、Redis 可独立部署；Python 要求来自本地 pyproject 的 >=3.13，最终以候选 HEAD 锁文件为准。不必重建整个平台 |
| 安全性 | 独立数据库、缓存、凭据、合成数据可隔离内部影响；若仍调用正式微信商户接口，外部资金、账单与风控仍真实发生 |
| 性能影响 | 独立资源可做锁竞争和故障注入；不要在容量有限的生产 2c2g 主机旁启高负载测试实例，避免共享 CPU/IO/连接资源影响用户 |
| 维护成本 | 长期环境有配置漂移、证书、域名和依赖维护成本；脚本化、固定版本和复用迁移可降低后续成本，但本次未交付环境脚本 |
| 兼容性 | 适合前后端完整联调、迁移演练与真实回调路由；仍需验证生产差异与存量 JWT/在途订单迁移 |

**结论与建议：**若团队会持续迭代支付和资产功能，保留独立测试环境很有价值；本次紧急修复先按[方案三](PR219-03-紧急止血与临时隔离验证方案.md)止血并做临时最小环境，不把专用测试商户申请或全量运维建设串成前置等待。

## 2. 事实基线及缺失项

- [最新评论](https://github.com/Jisalute/DS/pull/219#issuecomment-6317850785)仍列九条未完成项；PR HEAD `c1cd77438d077a7b612c6048620d60b8f8cae3ce`，本地 `6c2c2bae48c256d98b32987c691051fd99295cde`。从固定候选提交部署测试，不用本地旧版冒充 PR 最新版。
- 本地 `README.md` 提供 systemd/uv 启动方式；`docs/RELEASE_OPS_TASK2.md` 提供 MySQL 连接池、Redis、独立迁移和后台任务说明。
- 本次目录检查未找到 `docs/DEVELOPMENT.md`、Dockerfile 或 Compose 配置；不假定已经有一键测试环境。
- 本地 `main.py` 启动包含初始化数据库、订单过期和后台任务；配置中的 `SKIP_STARTUP_DDL` 只控制部分 DDL，不能据此宣称后台任务已禁用。待完成文档也记录导入副作用。
- 生产 MySQL 精确版本/隔离配置、实际商户模式、测试资质、可用测试 AppID、域名及部署资源未核实。实施前从运维配置/商户后台核实，不以本文示例代替。

## 3. 环境隔离清单

| 对象 | 要求 | 失败时处理 |
| --- | --- | --- |
| 应用 | 独立主机/容器、进程、端口、服务名、候选提交与锁文件 | 不与线上实例共享工作目录或可写配置 |
| MySQL | 独立实例和数据卷；匹配生产版本、引擎、隔离级别、SQL mode、字符集和索引；独立最小权限账号 | 连接配置缺失即失败，禁止回退生产地址；不能仅改库名却保留生产高权限账号 |
| Redis | 优先独立实例和凭据；防止锁、限流、任务队列、缓存互串 | 只改 Redis DB 编号不是完整安全隔离，不执行可能影响共享实例的清空命令 |
| 数据 | 合成 A/B 用户、甲乙商户、管理员、SKU、余额、券和订单；无真实客户手机号、地址、token、资金账本 | 不为省事整库复制生产；迁移边界用等结构合成历史数据 |
| 第三方 | 默认出口拒绝真实支付/短信/推送/物流，仅测试边界可达 | 不能把 `WX_MOCK_MODE` 视为所有外呼已隔离；启动前检查实际调用路径 |
| 任务与迁移 | 独立任务调度和锁空间；先显式迁移、再启动；审核所有导入/启动副作用 | 没有可靠关闭开关时实施必要隔离控制，不能靠猜测环境变量 |
| 文件与日志 | 独立上传/静态存储、日志目录，敏感字段白名单 | 测试文件不得写进生产静态目录或对象存储前缀 |
| 回调 | 独立 HTTPS 域名/路径及鉴权边界；核对商户、AppID、订单归属 | 未匹配本环境订单不能修改生产数据或返回虚假处理完成 |
| 密钥 | 本地功能测试用测试材料；真实联调由受控环境注入最小必需密钥 | 不复制生产 .env 到开发机/公开 CI；不提交凭据 |

如果不得已同物理宿主机，至少落实资源限额、网络隔离和独立持久卷；这仍不如独立主机，生产资源紧张时不采用。

## 4. 实施顺序与每层验收

### 第一步：先止血，环境搭建另行推进

封堵实际可达的越权/固定验证码高危入口，或发布经过最小验证的授权补丁；继续处理在途支付回调与对账。具体边界见[方案一第 3 节](PR219-01-生产直接验证方案与风险.md)。这一步不依赖真实短信商户申请完成。

### 第二步：构建可复现测试栈

1. 固定候选 SHA，记录生产与测试版本/配置差异；复用项目锁文件及迁移，不随意升级 MySQL/Python/支付 SDK。
2. 新建无生产权限的 MySQL/Redis 和测试账号，网络层拒绝生产 DB/缓存访问。
3. 先执行隔离迁移并检查表引擎、唯一约束、审计列、状态字段。不要通过启动时动态加列掩盖迁移缺失。
4. 生成合成场景数据。首次启动前审核调度、物流、短信、微信和推送出口；有风险的未知外呼保持拒绝。
5. 健康检查仅证明可连接，不能代替业务验证。服务启动后通过真实 HTTP 路由执行登录/本人查询/拒绝越权等冒烟。

### 第三步：完成所有不需要真钱的验收

执行[逐项清单 U1—U8](PR219-04-逐项整改与验收清单.md)：真实 MySQL 双连接、真实事务、进程重启恢复、回调故障注入与重放、验证码并发核销、JWT 撤销、授权矩阵、内容边界、日志白名单。

支付/短信替身仅位于外部边界；应用内部实际路由、服务、SQL 与事务不能全被 mock 掉。模拟微信接口“退款受理成功后断连”，观察本地退款意图在重启后用原号查单；提交失败用真实 MySQL 验证回滚，不能只验证假 cursor 调了 rollback。

实际 MySQL 两连接记录不同 `CONNECTION_ID()`；测试时保留故障前的隔离数据，重启后继续恢复。重建空库再成功跑一遍不叫恢复证明。

### 第四步：接真实服务，限制在专用主体

- 短信供应商配置与模板审核完成后，只向内部授权号码发送。观察请求受理、投递/手机收到、用途绑定核销、改密和旧凭证失效。
- 微信支付产品/商户确定后，优先使用专用测试商户/子商户与测试应用（是否能取得需核实）；如只能用现有正式商户，外部账务仍不隔离，需维护者明确批准内部测试订单和预算。
- 逐笔验证下单、支付、真实验签回调、查单、退款受理、最终退款结果、对账；不能把异步 PROCESSING 当成成功终态。
- 通知 URL 不应直接修改整个正式商户的默认地址而转走客户通知。只有确认所用接口支持、且项目能对这批测试订单显式指定正确回调时才使用测试 URL；不支持安全路由时，在已加固生产路径做内部最终冒烟，而不是强改全局回调。
- 测试订单号使用独立业务身份，接收端还须核实真实商户/订单关联；前缀只能帮助追踪，不是权限隔离。

### 第五步：前端与发布演练

完整覆盖六项前端迁移：Bearer、去旧 key 授权、本人作用域、401/403、服务端金额/数量、先发送再核销。用实际小程序体验版/批准测试版本验证；若源码或账号不可用，前端验收维持阻塞。

迁移演练覆盖存量 JWT 失效、在途支付/退款接管、未知退款对账、后台任务单点。生产切换后的少量内部冒烟仍需要，但不再承担首次发现核心故障的责任。

## 5. 为什么不能把 0.01 元当作充分证明

- 正式微信接口调用仍产生真实交易，可能有账单、费用、风控和到账延迟；小金额不等于沙箱。
- 一分原单无法做正金额的部分退款；多个退款、分摊舍入、券/积分抵扣、大额上限需独立场景。
- 一次正常成功不会自然触发提交失败、网络结果未知、并发审核、非法归属、订单状态覆盖。
- 两环境如果共享生产 DB、Redis、调度或全局回调，哪怕只付一分钱也可能影响真实客户。
- 没有核实对目标产品和商户通用的“0.01 元必可用”承诺；实际额度与可用性需按商户规则确认。

## 6. 进度、成本与停止条件

不在缺少资源和商户资质信息时承诺固定小时数。“完整测试环境很慢”主要可能来自域名/商户/短信审批及配置迁移，不是每项安全测试都必须等待这些依赖。

- 立即可并行推进：后端最小修复、合成数据、隔离 MySQL、故障/并发测试、前端请求层迁移。
- 外部依赖可能较慢：短信签名模板审批、测试商户/子商户、应用绑定、真实回调网络与证书授权。
- 等待外部依赖时对应功能保持不可用/内部限定，不阻塞已完成独立安全补丁发布。
- 发现生产凭据、生产地址、跨环境通知或未知后台副作用立即停止测试，先修隔离；资产差异、重复退款、越权成功则禁止放量。

回退保留修复后的授权边界；数据库恢复与外部资金对账分别处理，不能恢复本地快照后盲目重新发起已成功的退款。

## 7. 官方与研究依据

- [Testcontainers Python MySQL](https://testcontainers-python.readthedocs.io/en/latest/modules/mysql/README.html)：临时容器可以运行真实 MySQL，支持指定镜像和凭据。本文不要求新增依赖，Docker/独立 VM 同样可以；示例默认 latest 或旧示范版本不应照抄，须匹配生产。
- [MySQL 锁定读](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)、[InnoDB 错误处理](https://dev.mysql.com/doc/refman/8.4/en/innodb-error-handling.html)：普通读取不保护后续写入；锁超时与死锁回滚范围不同。引用 8.4 文档不表示 DS 生产就是 8.4。
- [微信 v2 支付验收指引](https://pay.weixin.qq.com/doc/v2/merchant/4011984810)：限定 v2 付款码仿真能力，不足以证明小程序/API v3 退款通用沙箱可用。本次未确认可用的通用境内 v3 沙箱；不能拼造 sandbox URL。
- [微信退款](https://pay.weixin.qq.com/doc/v3/merchant/4013071036)、[通知](https://pay.weixin.qq.com/doc/v3/merchant/4013071196)：稳定退款号、幂等、最终查单；真实回调不能由替身完全代替。
- [阿里云测试短信](https://help.aliyun.com/en/sms/user-guide/send-test-messages-1)：测试短信也收费，存在绑定号码与资质/模板要求。仅作供应商示例，不表示 DS 已选阿里云。
- RIFL、LDFI、Elle 三篇论文与边界见[方案三研究依据](PR219-03-紧急止血与临时隔离验证方案.md)。它们支持确定性故障/事务验证的必要性，不保证环境搭好就安全。
