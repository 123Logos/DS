# 方案三：紧急止血＋临时隔离验证＋最后受控真实联调（推荐）

日期：2026-10-24。**推荐选择本方案：不等完整预生产环境建好，也不拿真实用户做故障实验。先降低现网风险，使用最小隔离栈关闭核心缺陷，最后把小额真实支付/短信仅用于外部集成验收。**

## 1. 决策与三方案比较

| 方案 | 现网风险降低方式 | 内部失败/并发验证 | 真实外部集成 | 主要限制 | 结论 |
| --- | --- | --- | --- | --- | --- |
| [一：直接生产验证](PR219-01-生产直接验证方案与风险.md) | 直接上线；未验证改动也可能引入新风险 | 无法安全制造资金/数据库故障 | 最接近真实配置 | 客户、账本、库存、回调都可能受影响，代码回滚不能撤销外部资金动作 | 不用于未完成整改的主验收 |
| [二：完整独立测试环境](PR219-02-独立测试环境与小额联调方案.md) | 仍需另行先止血 | 可完整、可重复 | 独立接入后可验 | 资源、域名、资质审批可能延迟；正式商户资金并不自动隔离 | 长期值得建设 |
| 三：本方案 | 最小安全补丁/暂时关闭高危入口先行 | 临时真实 MySQL/Redis＋合成数据＋外部边界替身 | 最后限定内部主体逐笔验收 | 要严守门禁，临时环境不能漏掉调度、网络和凭据隔离 | 最符合当前“快速修复且不影响用户”的目标 |

不承诺未经核实的搭建时长。此方案缩短的是依赖链：权限修复和真实数据库测试不必等待支付商户、短信模板及完整测试前端环境全部就绪。

## 2. 技术方案可行性评判

**提出的方案：**将应急止血、核心正确性验收、第三方真实联调拆开推进。

**评判结果：**有条件可行，推荐作为本轮执行方案。

| 维度 | 分析 |
| --- | --- |
| 技术可行性 | 复用 FastAPI、PyMySQL、MySQL、Redis、现有迁移及 pytest；最小栈可用独立容器或一次性 VM，不需要引入消息总线/微服务 |
| 安全性 | 可达高危入口优先止血；故障注入仅在独立实例；真实资金最后验证并限主体、笔数、金额；不承诺零业务影响 |
| 性能影响 | 生产不承受竞争压力和故障实验；JWT 服务端撤销检查会增加读开销，真实压测和指标确认后再考虑缓存，不用延迟撤销换速度 |
| 维护成本 | 相比完整预生产少维护非必要组件；场景、迁移和合成数据可留下复用，临时实例用完销毁；持久退款恢复逻辑属于必须的产品能力，不是测试专用逻辑 |
| 兼容性 | 必须安排前端 Bearer/401/403 迁移、存量 JWT 失效通知、在途订单与退款接管；新旧服务不可绕过同一授权/幂等规则 |

**结论与建议：**用较小的隔离环境缩短等待，用验收门禁控制上线范围，而不是用更小的交易金额代替正确性证明。

## 4. 阶段 A：先把可达高危能力关住

负责人：维护者＋后端＋运维；产物：明确的线上防护范围、最小补丁及合法用户冒烟证据。

- 从实际部署记录确认现网版本；如果未部署 PR 的授权修复，不等短信接入，先关闭匿名退款审核/资金写入/固定码找回等入口或发布经过验证的最小修复。
- 枚举所有实际路由与别名，不只改常规 `/refund/audit`，还覆盖评论指出的 `/merchant/approve_refund`、财务写入口、商家发货/订单和个人资产查询。
- 资金和本人资产由服务端认证身份决定；管理员由服务端配置决定。网关只能临时缩小入口，不能替代资源归属校验。
- 未闭环的短信找回暂时明确不可用；有需要时使用既有、经过身份核验的人工客服流程，不能临时发万能码。
- 未证明安全的自动退款可以暂缓新申请的自动执行，保留申请及人工核对能力；不得重复提交到另一条退款链路。
- 对已支付或退款中的订单，继续可信通知处理与主动查询；不得一并关闭回调，或固定 ACK 掩盖数据库失败。
- Bearer 迁移和合法本人退款查询与权限补丁一起验收，避免“封住越权但正常用户全被拒绝”。对影响存量客户端的变化明确通知，不保留匿名/旧共享 key 后门。

**退出门禁 A：**匿名/越权请求不触及敏感数据与资产；合法本人/所属商家/管理员操作符合契约；临时停用边界已告知，未修复资金功能不对公众开放。门禁 A 可支持最小安全补丁发布，不代表整个 PR 完成。

## 5. 阶段 B：最小但真实的隔离栈

负责人：运维/测试建立环境，后端核对副作用；产物：版本指纹、网络边界、合成场景数据。

必要组件仅包括：候选后端、与生产版本/配置一致的独立 MySQL、业务确实依赖时的独立 Redis、外部支付/短信/审核边界替身及 HTTP 驱动。没有必要先复制整套运维大盘、生产客户数据或完整服务器拓扑。

实施顺序：

1. 固定候选 SHA；从运维信息确认 MySQL 精确版本、引擎、隔离级别、SQL mode、字符集及相关索引，不凭经验选择最新版。
2. 在非生产宿主机运行一次性容器/VM。独立数据卷、凭据、端口和网络；限制资源，不与生产争抢 IO。
3. 只注入测试配置。默认拒绝到生产 DB/Redis/支付/短信/推送的网络出口；不要复制生产 `.env`。默认地址或配置回退不能偷偷连到生产。
4. 审核导入、startup、迁移、调度和后台线程。先迁移后启动；需要调度恢复测试时仅让它操作隔离记录。控制点不存在就补必要控制，不把未实现的 `DISABLE_*` 变量写进计划冒充可用能力。
5. 生成 A/B 买家、甲乙商户、管理员、1 件库存、恰够一笔发券的余额、各状态订单及短信挑战。测试账户不能持有生产身份 token。
6. 通过实际 HTTP 路由走业务；MySQL 用两个真实连接记录 `CONNECTION_ID()`，连接必须在整个事务内保持一致。

**退出门禁 B：**能证明无生产连接/外呼，真实业务能使用合成数据运行，实际事务和外部边界可控。只有“容器启动”“/ready 返回成功”不够。

工具选择：优先现有 Docker/WSL2/独立 VM 能力；Testcontainers 可用但不是必需。当前项目没有该依赖，本次不为方案安装库。没有容器运行时，可用临时云主机或受限独立 MySQL 实例，不以“必须先建设 Kubernetes”为前提。

负责人：后端实现＋测试验收；产物：固定提交的回归、HTTP 冒烟、MySQL 事务历史与恢复记录。

| 整改集合 | 做法 | 不可替代的退出证据 |
| --- | --- | --- |
| U1/U2 短信与撤销 | 供应商适配先用边界替身；真实 MySQL 中核销/改密/撤销同事务；所有认证类型检查服务端有效性 | 错误次数不回滚；重发不绕上限；两连接仅一次核销；改密后跨实例旧 token 均失效 |
| U3 退款 | 先提交稳定退款意图，再调用外部；未知状态用原号查询/重试；审核和直接退款共用业务身份 | 外部成功、本地失败、重启/超时/重复申请都只产生一次逻辑退款，状态能恢复 |

| U7 内容 | 审核所有公开嵌套文本和最终快照；单项超限拒绝，非 pass 不公开 | 2499/2500/2501、Unicode、嵌套、整体超限但单项合法、新增修改、异常分支均覆盖 |
| U8 权限/日志/审计 | 实际路由完整身份矩阵；敏感哨兵值触发正常与异常日志；审计可信来源 | 非法无副作用、合法本人成功；敏感值不外泄，资金事件可追踪 |

### 必测失败切点

- 本地退款意图提交前失败：外部没有调用。
- 意图已提交、调用前进程终止：重启从持久记录继续，退款号不变。
- 外部已受理、响应丢失：记录结果未知，原号查单，不能换号重退。
- 外部成功、本地最终写入/commit 失败：重启后查到外部终态，补齐本地一次副作用。
- 本地已 commit、HTTP 响应丢失：客户端/微信重试读取原完成结果，不再次记账。
- 同一业务由不同实例、不同通知 ID 并发触发：靠数据库约束和事务保证效果一次，不能仅依赖进程锁。
- 锁等待超时、死锁、唯一冲突：显式处理事务边界。MySQL 锁超时默认可能只回滚当前语句，应用必须清理整笔失败业务，不能假设全部自动撤销。

网络代理断网能制造未知结果，却不能保证刚好发生在 commit 后；用测试专用屏障或可观察提交证据定位切点。测试钩子不作为公网参数/生产后门暴露。

### 关于“回调收到就先 200”的取舍

微信官方允许快速应答后异步处理，而 PR 本轮要求本地业务持久化完成后确认。因此默认选短同步事务满足原验收口径。若超过 5 秒窗口，需单独批准改为持久 inbox：可靠保存事件后 ACK，异步处理、重试、查单对账。**入内存队列、写普通非可靠日志或仅验签后直接 ACK 不能替代可靠持久接收。** 采用 inbox 时应明确“接收成功”与“业务完成”的不同指标，不能悄悄把本地失败仍 200 的问题换个名字。

**退出门禁 C：**共用清单对应行为全部有具体结果；不得以测试数量、静态检查或一次正常支付代替。没有外部账号仍可以完成此阶段，但 U9 和 U1 的真实投递保持未验收。

## 7. 阶段 D：真实服务只做无法被隔离测试证明的部分

负责人：维护者批准＋授权内部操作员＋对账人；产物：真实配置和协议链路证据。

### 短信

选定供应商并获得签名/模板许可、费用额度、授权内部手机。服务端真实发送→供应商受理/投递→手机收到→仅找回密码用途核销→旧 token 失效。发送接口完整文档需先落地，前端按“先发再核销”对接。不把供应商返回成功等同于手机收到，也不把手工插库当签发闭环。

### 微信支付/退款

1. 确认当前实际产品为普通商户、普通服务商还是其他平台产品，使用对应契约；服务商保存并校验 sub_mchid，不混用接口。
2. 优先独立测试主体；若必须用正式商户，则仅对授权内部用户、商户、SKU、订单执行。后台控制白名单、单笔、笔数和累计预算；不能只靠前端隐藏。
3. 产品允许时用 0.01 元覆盖支付和全额退款；部分退款需要更高原始金额，另批预算。金额小不保证不触发风控，不承诺即时到账。
4. 验证真实签名/证书、API 权限、AppID 绑定、回调公网可达、真实查询及账单一致。生产私钥只在受控运行环境中使用，不复制到开发机或文档。
5. 新增测试 URL 不能抢走现有生产默认回调；无法安全按订单指定路由时，在通过前置门禁的生产路径做内部最终冒烟。任何客户订单都不参与故障注入。
6. 交易及退款终态确认后保留合规审计，不手工删账。未决状态必须记录责任人与下一次查询/处理，不能“看着差不多”关闭验收。

本次检索未确认有通用境内 API v3 支付/退款沙箱；查到的是有限定范围的 v2 仿真。若商户支持提供专属测试能力，先核对产品和契约，不自行拼 `sandboxnew/v3` 地址。

**退出门禁 D：**对应真实短信与微信支付/退款、通知/查询及对账闭环成功。未通过的功能保持停用或严格内部限定；不因其他功能通过就一起开放。

## 8. 阶段 E：发布、回退与在途状态接管

- 先发布范围清晰的安全修复，再开放通过门禁的业务。安全鉴权修复不能随机只给 1% 用户生效而保留其余越权入口。
- 正式开放前覆盖六项前端迁移：Bearer、去旧共享 key 授权、本人作用域、401/403、权威价格与正整数数量、发码再核销。实际小程序源码未在本次修改；其验收单独记录。
- 在途支付/退款建立清单。已有未知退款先用原号/渠道信息查询对账，不批量给历史记录生成新退款号再次调用。无可信身份的历史异常转人工核实。
- 数据迁移先增加必要字段/约束并处理历史数据，核对在线 DDL 影响；禁止请求处理中临时 ALTER TABLE 作为稳定上线方案。新增唯一索引前处理重复记录要保留审计，不能直接删除账本。
- 新旧实例混跑必须遵循同一状态和幂等协议；若旧版仍可绕过，新资金写入暂停并受控切换，不能以滚动发布为由保留旁路。
- 可按内部主体再逐步扩大新版流量，但同一订单必须有一致处理路径；后台任务和回调也要纳入切换，不能只路由前台请求。
- 监控授权异常、认证误拒绝、支付退款未知状态、回调失败率/时延、待恢复任务积压、锁等待/死锁、余额库存不变量及敏感日志。关键资金/越权不变量出现一次即停止放量。
- 回退目标必须保留阶段 A 防护。程序回退不撤销外部退款；不通过恢复数据库快照抹去已发生的微信交易，而应逐笔查单与审计补偿。

## 10. 研究与官方依据：支持什么，不支持什么

### P1：RIFL——稳定请求身份与结果持久化

Collin Lee、Seo Jin Park、Ankita Kejriwal、Satoshi Matsushita、John Ousterhout，**Implementing Linearizability at Large Scale and Low Latency**，SOSP 2015，DOI `10.1145/2815400.2815416`。

一手来源：[SOSP 官方摘要](https://www.sigops.org/s/conferences/sosp/2015/archive/abstracts.html#2015-126-lee)、[论文全文](https://sigops.org/s/conferences/sosp/2015/current/2015-Monterey/126-lee-online.pdf)。

- 论文依赖唯一 RPC 身份、持久完成记录、重试定位原结果与安全记录回收；完成记录和业务变化必须原子持久化。
- 对 DS 的应用推导：退款/发券有稳定业务身份，本地资产变更和完成标记同事务，响应丢失后读取原结果；测试进程重启、迟到重试。
- **不能推出：**加一个 Redis 锁或 request ID 就 exactly-once；MySQL 事务能回滚微信退款；论文性能数字可移植到 DS。此处追求可证明的幂等业务效果，不承诺跨 MySQL 与微信的魔法原子事务。

### P2：LDFI——从成功结果反推高价值故障切点

Peter Alvaro、Joshua Rosen、Joseph M. Hellerstein，**Lineage-driven Fault Injection**，SIGMOD 2015，331–346，DOI `10.1145/2723372.2723711`。

一手来源：[作者论文](https://people.ucsc.edu/~palvaro/molly.pdf)、[ACM 出版页](https://dl.acm.org/doi/10.1145/2723372.2723711)。ACM 直读受限，作者全文和出版索引可核实题名、作者与会议。

- 论文沿正确结果的依赖向后分析故障组合，使用数据血缘与 SAT 求解，不是无目的随机断网。
- 对 DS 的应用推导：围绕“不能重复退款”“不能部分入账”，在持久意图、外部调用、最终提交、HTTP ACK 等位置安排少量确定性失败用例；这是方法借鉴，不要求引入 MOLLY。
- **不能推出：**手写用例享有论文的形式化覆盖保证；论文已证明 DS 崩溃恢复。论文保证有输入、配置和有界故障模型前提，原模型不覆盖 crash-recovery 或 Byzantine；本文的重启测试是额外工程验收。

### P3：Elle——检查事务历史，而不是只看成功响应

Kyle Kingsbury、Peter Alvaro，**Elle: Inferring Isolation Anomalies from Experimental Observations**，PVLDB 14(3)，268–280，2020 年出版，对应 VLDB 2021，DOI `10.14778/3430915.3430918`。**不是 OSDI 2020。**

一手来源：[作者 arXiv 摘要](https://arxiv.org/abs/2003.10554)、[PVLDB 官方卷期说明](https://www.vldb.org/pvldb/vol14/FrontMatterVol14No3.pdf)、[正式出版页](https://dl.acm.org/doi/10.14778/3430915.3430918)。

- 论文从可观察事务历史推断依赖与隔离异常，要求工作负载能暴露必要版本关系；摘要的异常覆盖声明排除 predicates。
- 对 DS 的应用推导：记录双连接历史、开始结束和数据库最终余额/库存/券/账本，用不变量发现反例，不只统计 HTTP 200。
- **不能推出：**两条并发请求即证明所有交错正确；数据库隔离正确即鉴权正确；未适配/运行 Elle checker 就可以写“通过 Elle”。本文没有运行该工具。
