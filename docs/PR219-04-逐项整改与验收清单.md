## 2. 九条未完成项如何关闭

### U1：真实短信签发、发送、用途绑定与核销

实施入口：`api/user/routes.py`、用户 schema、现有验证码存储与认证服务；先复用现有结构，不另起一套身份体系。

1. 选定一个实际供应商，配置凭据、签名、模板、区域、超时及发送结果查询/回执；做一个明确的服务边界即可，不为了“可配置”先实现多个供应商框架。
2. 服务端用安全随机数生成验证码；保存不可直接还原的校验值。短数字码仅做普通哈希仍易离线枚举，可采用独立服务端秘密参与的 HMAC；秘密不进入日志。记录目标手机号/用户、用途、签发身份、到期时间、失败计数、发送状态、核销状态。
3. 先可靠创建发送记录，再调用供应商。明确“请求受理”“供应商受理”“投递”“已核销”的差别；发送失败不可伪装成成功。对受理结果不明的请求，用供应商能力查询；无幂等能力时不得盲目重发并宣称只发送一次。
4. 同时限制手机号/账号、IP、设备及总发送额度；核销另设失败计数。重新发送不能成为清零连续猜码次数的旁路。限制新码与旧码的有效关系，保守选择仅最新可用码有效。
5. 固定用途如找回密码只能用于改密，不能用于注册或换绑；目标必须来自可信业务绑定。响应与耗时策略避免泄漏手机号是否注册。
6. 错误次数在可靠事务中提交，不能随后被业务异常回滚；成功核销、密码更新和撤销旧会话必须原子提交。单条码使用行锁或条件更新防重复消费。
7. 不提供固定万能码、手工插库“开通”、审核失败放行等生产兼容路径。发送接口完整契约需落到 `docs/api/`，路径和字段由实施时确认；本文不冒充现成发送接口。

验收：真实 HTTP 发送→内部授权手机收到→仅指定手机号/用途核销→改密；错误达到上限后正确码仍拒绝；过期、旧码、错用途、跨手机号拒绝；两个独立连接并发核销仅一次成功；失败密码更新不能消耗码并留下半完成状态；供应商拒绝、超时、重复发送均有明确状态。记录供应商消息 ID 和脱敏结果，不保存明文验证码。

无真实服务时可以关闭本地逻辑缺陷，但“真实短信投递闭环”必须保持待验收。OWASP 找回密码指南及 NIST 依据见本文参考资料。

### U2：JWT 与所有会话类型的完整撤销

实施入口：`core/auth.py`、登录签发点、改密/退出/禁用入口及全部认证依赖。

- 推荐复用现有 sessions：新 JWT 带可信的会话标识 `sid`，验签、时效等通过后，每个受保护请求仍核对服务端会话存在、未撤销及归属。若业务需要“全部设备失效”，可采用用户级认证版本统一失效；二选一作为主机制，不同时堆叠多套冗余方案。
- 所有 UUID/opaque session/JWT/refresh token（如有）都纳入同一撤销约束；任何旧认证分支不得绕开。只有删 sessions 而 JWT 不查询它，仍不成立。
- 无 `sid` 的存量 JWT 不得回退到“只验签即可”；一次性失效并要求重新登录，或有明确定义的安全迁移截止。要宣称改密后立即撤销，就不能保留继续可用的旧格式旁路。
- 多实例必须看到同一撤销状态。初期直接查询权威存储最简单；缓存必须定义失效传播，否则不能承诺即时撤销。短 JWT 有效期不是立即撤销的替代品。
- 改密与撤销同事务完成；认证存储不可用时，受保护操作不能默认放行。单纯轮换所有人的签名密钥会造成全体掉线，不作为常规按用户撤销方案。

验收：改密前获取每种支持的 token，改密后跨实例请求均拒绝；新登录成功；其他用户不受影响；并发刷新/签发不能重新获得旧身份状态的有效凭证；退出、禁用等按各自契约验证。旧客户端清除本地 token 不能替代服务端证据。

### U3：审核退款与直接退款统一持久幂等和恢复

实施入口：`api/order/refund.py`、`api/order/merchant.py` 的审核入口、实际退款服务及支付客户端。

- 各入口汇入同一退款业务操作。先在本地短事务内检查归属、权限、可退金额和当前状态，创建稳定退款意图、不可变金额/商户信息、`out_refund_no`，再提交；提交成功之前禁止调用微信。
- 为同一逻辑退款定义稳定业务身份及唯一约束。只依赖客户端每次随机生成的 key 不够：并发审核即使传不同 key，也必须识别同一退款申请。允许部分退款时，不能简单让整张订单只能有一条退款，而应按退款申请区分，并在订单锁下预留累计退款额度。
- 普通商户退款号在商户系统内唯一；普通服务商退款号在服务商系统内唯一，并保存 `sub_mchid`。不能只按子商户缩小唯一范围。
- 外部调用在数据库事务外进行，避免网络延迟占住余额/订单锁。已有持久退款记录可承担待处理任务职责；不要求新引入 Kafka、微服务或分布式事务框架。
- 超时/断连属于结果未知，不等于失败。记录待查询状态，以原退款号查询；符合微信契约时用原号、原参数重试，禁止换新号。API 受理成功不等于退款完成。
- 回调和主动查询进入同一幂等终态处理事务；退款状态、账本、积分、券只变动一次。每笔资金副作用有稳定业务事件标识和唯一约束；同 key 不同金额/订单拒绝。
- 持久任务恢复必须能从进程重启后继续；有频率限制、退避、告警、人工对账出口。记录不能在资金未对平前被 TTL 清理。

验收：直接退款与审核并发、重复点击、同 key 不同参数、同申请不同 key、微信受理后断连、本地最终提交失败、进程在外部成功后被终止、恢复后再次执行；始终保持同一逻辑退款身份，不超退款，账本只记一次。必须有外部与本地状态对账证据，不仅断言返回码。

### U4：支付/退款回调持久化后才确认，失败可重放

实施入口：`api/wechat_pay/routes.py` 全部实际注册通知路径，包括线上、线下及服务商分支（若启用）。

- 验证原始报文签名、证书/公钥、解密和商户归属；核对订单身份、金额、币种、状态。无效通知不得触发资产变化。
- 本轮默认采用短同步事务：订单状态、结算、积分/券和通知幂等标记全部提交后，才返回 API v3 成功确认 HTTP 200/204。异常传到协议边界返回失败，数据库故障建议 5xx，不能吞异常后回复成功。
- 已完成的重复通知，只有确认此前已持久化全部副作用后才回复成功；先写“处理完成”再结算会丢业务。重复通知可能具有不同通知 ID，去重还要绑定交易/退款业务身份，不能只看通知 ID。
- 微信要求快速应答。若同步业务不能稳定在官方 5 秒窗口内完成，另行设计持久 inbox：验签并将完整必要事件可靠提交后 ACK，异步幂等消费、可重试、查单补偿。此时“成功 ACK”表示可靠接收，不表示业务处理完成，必须明确修改验收口径并得到维护者批准，不能偷偷降低本轮“全部本地业务提交后确认”的要求。仅入内存队列就 ACK 不合格。
- 通知重试次数有限，不能只等微信再次发送；增加支付/退款查单对账闭环。客户端跳转或返回页不能被当成支付成功证据。

验收：在订单更新、结算、积分、券、幂等标记及最终 commit 各点注入失败，观察不返回成功且无部分提交；恢复并重放完成一次；再次及并发重放均无重复副作用。实际 HTTP 层验签用测试专用密钥和合法测试报文完成，不在生产开启免验签入口。真实微信签名兼容性留到最终受控联调验证。

### U5：全部并发状态迁移有原子性证据

实施入口：`api/order/order.py`、发货与退款所有入口、支付通知和订单过期后台任务。

- 列出真实状态枚举与每一条迁移、发起角色、前置状态、归属、库存/资产副作用。先保留业务允许的转移，不能猜测“收货一定战胜退款”。
- 使用同事务 `SELECT ... FOR UPDATE`，或带原状态、归属/版本条件的 UPDATE；检查影响行数。单纯先 SELECT 后无条件 UPDATE 不合格。
- 多表保持固定锁顺序；死锁/锁超时要回滚整笔事务，外部资金调用不藏在自动重试事务中。状态变更和相关本地副作用要一起提交。
- 用户可调用接口不得设置已支付状态；仅可信验签回调或查单结果可触发。过期关闭与支付成功竞态也须覆盖。

验收：两独立连接在可控屏障下竞争退款/收货、退款/发货、重复发货、重复收货、支付/超时关单；同时测试两种先后交错。结果必须是业务允许的串行结果，不能把退款中覆盖回普通履约状态，失败一方无残余副作用。场景须调用实际业务路径，不能只验证孤立的示范 SQL。

### U6：真实 MySQL 库存、余额、发券竞争

- 使用独立实例，MySQL 版本、InnoDB、隔离级别、字符集、SQL mode、索引与生产一致；版本目前未核实，不擅自固定为 8.0 或 8.4。
- 从同一待验收提交生成表结构，迁移先在合成数据上演练；测试账号无生产权限。两连接记录不同 `CONNECTION_ID()`、autocommit 与隔离级别，用屏障/事件控制竞争，不靠随意 sleep 或串行提交伪造并发。
- 库存初始 1：两个不同合法购买请求最多一个成功；库存不负数，失败方无订单明细或扣款残留。
- 余额只够一笔发券：两个不同逻辑请求竞争最多成功一个；余额变化、券数和流水一致。相同发券业务请求重放只扣款发券一次；同 key 不同参数拒绝。
- 提交前断连/异常：整个事务回滚；提交后客户端未收到响应：用原幂等身份重试获取原结果。连接池不得把带未提交事务的连接交给下一请求。
- HTTP 并发测试与数据库终态断言同时保留，至少覆盖所有上述交错；重复跑用于捕捉非确定性，但次数本身不是正确性证明。

验收材料：服务器版本与配置、迁移版本、连接 ID、交错时间线、请求/业务身份、前后库存余额券及流水、命令和退出码。SQLite、单连接替身、“没有报错”都不能替代此项。

### U7：商品属性/SKU 全部公开文本逐项审核

实施入口：`api/product/routes.py`、商品与规格 schema、现有微信内容审核服务。

- 依真实 schema 枚举名称、描述、属性名与值、SKU 规格名与值、所有嵌套公开文本。把最终待保存结构中的文本提取出来逐项审核，不把整个 JSON 串拼成一段送审；不审内部 ID 和非公开机器字段。
- 规范化后审核同一份不可变待保存内容；全部明确 pass 才能公开落库，review/risky/超时/异常均不放行。更新时审核最终结果，防止旧未审核字段或并发更新混入。
- 官方 v2 `content` 上限为 2500 字、UTF-8 编码，不是“2500 字节”。本轮保守策略：单项超过 2500 字拒绝并给字段路径，不截断后保存全文，也不声称随意切块审核等价于全文语义审核。若业务必须更长文本，另行确定可接受的完整审核策略。
- 测试 2499/2500/2501 边界、中文/emoji/组合字符、深层数组对象、多项分别小于上限但合计超限、空文本、修改和新增、上游异常、仅嵌套字段违规。明确 Unicode 计数规则，真实微信边界未联调前不声称所有字符计数完全一致。

验收：任何违规或错误时商品及 SKU 均无部分公开写入；落库内容与送审快照一致。真实审核需授权 AppID/AppSecret 和近两小时访问过小程序的 openid；模拟 verdict 只能证明本地控制流。

### U9：未用真实服务/生产证书/资金数据，应该如何处理

“未用生产数据”不是缺陷，不要求复制客户资金账本来补证据。

- 在隔离环境先完成逻辑、权限、事务、恢复与报文校验；只用合成用户、商品、余额和券。
- 最后用内部授权手机号验证真实短信；用专用测试商户/子商户（若可得）或生产批准的内部测试主体做真实支付、查询、回调、退款、对账。不能假设有通用 API v3 沙箱。
- 生产证书/私钥只由有权限的运维在受控运行环境注入，不复制到开发机、公开 CI、文档或评论；测试可用独立密码学材料，不把它叫真实微信验签证据。
- 0.01 元若产品允许，只覆盖最小支付/全额退款。部分退款必须有大于 1 分的原单，普通金额的优惠分摊、舍入、上限等在合成数据里完整测试。金额、笔数、累计支出和唯一订单白名单都需限制。
- 真实验收期间禁止故意损坏生产数据库、杀进程制造丢单、反复乱序重放客户通知。上述故障已在隔离环境验证。

外部验收不能通过的对应功能保持关闭/待验收，而不是把 mock 或证书占位值当真。没有申请本次真实交易权限；本次不发生扣款或短信发送。

## 3. 六条前端迁移清单

| 原评论影响 | 必须实施 | 验收与兼容边界 |
| --- | --- | --- |
| Bearer | 统一请求层为受保护请求附 `Authorization: Bearer <token>`；登录、找回申请及微信服务端通知按各自契约，不盲目给所有 URL 附 token | 正常登录、过期、改密后失效、多端验证；禁止把 token 发给第三方域名或写日志 |
| 管理员权限 | 删除通过 admin_key/key 授权的假设，后端由 `ADMIN_USER_IDS` 等可信配置判断 | 配置合法管理员；普通用户即使携带旧 key 仍拒绝；旧字段是否兼容输入按最终 API 文档，兼容输入不等于授予权限 |
| 本人作用域 | 券、捐赠、个人资料、本人券和积分使用当前认证用户；请求 user_id 不能切换账号 | A/B 两用户测试；管理员代操作只走明确授权契约，不能复用普通用户界面绕过 |
| 401/403 | 401 清除失效凭据并引导登录；403 展示无权且不无限重登；区分业务冲突和暂时不可用 | 未登录和越权都由后端阻断；资金写请求不做未知结果下的新 key 自动重试 |
| 价格与数量 | 展示服务端金额；旧 price 如仍兼容仅为非权威输入；数量传 JSON 正整数 | 篡改价格不改变订单金额；非法数量拒绝；不能为了测试把公开商品改成 0.01 元 |
| 短信找回 | 待发送接口完整契约落地，改成“申请发送→核销改密”；显示冷却/失效/失败状态 | 无固定验证码、无前端生成可信验证码；无供应商时明确不可用，不伪造发送成功 |

未在本次取得或修改小程序源码。前后端同一发布批次联调；旧客户端不兼容时不能回退到匿名/共享 key 放行，应明确最低可用版本或暂时关闭对应操作。

## 4. 发布门禁与证据记录

每个改动独立记录：任务 U 编号、commit SHA、改动路径、迁移版本、运行环境、准确命令/HTTP 场景、实际结果、DB 不变量、外部边界、未完成依赖。不要预写“通过”。

- 门禁 A：可达高危入口已封堵；合法用户冒烟与拒绝后资产不变验证通过。可单独发布最小安全修复，不代表整个 PR 完成。
- 门禁 B：U1—U8 的本地与 MySQL 专项场景通过，失败恢复可重放，前端迁移通过；涉及资金的未验收功能不得向一般用户开放。
- 门禁 C：对应真实短信、微信支付/退款、回调查单对账通过；全量发布前确认在途订单和历史未知退款如何接管。
- 合并范围由维护者书面确认；拆分整改需保留跟踪事项及阻断状态，不能把尚未通过 B/C 的项标记已完成。
