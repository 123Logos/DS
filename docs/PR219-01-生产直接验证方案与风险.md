# 方案一：直接部署生产验证——不作为未完成安全整改的验收方案

日期：2026-10-24。结论：**否决“把尚未证明正确的资金/并发修复直接全量上线，边服务真实用户边找问题”；有条件允许已验证的最小止血修复发布，以及最后的内部账号小额冒烟。**

## 1. 适用事实

[PR #219 最新评论](https://github.com/Jisalute/DS/pull/219#issuecomment-6317850785)仍声明短信、JWT 撤销、退款持久幂等、回调持久化确认、事务竞态、MySQL 双连接、内容边界及专项测试未完成。当前 PR HEAD 是 `c1cd77438d077a7b612c6048620d60b8f8cae3ce`；本地是较早的 `6c2c2ba…`。本文依据评论制定方案，不替作者确认整改完成，也不把 PR 等同于当前生产版本。

现网已上线是用户提供的事实；生产具体提交、MySQL 版本、商户类型、网关能力、日交易量和密钥状态未核实。本次未登录生产、未执行测试交易。

**速度应衡量“多久阻止继续发生风险”，而不只是“多久把一个版本部署出去”。** 退款外部成功、本地未记账时，回滚程序也收不回已退的钱；账号被接管、隐私被读出，同样不能靠回滚撤销。

## 2. 技术方案可行性评判

**用户提出的方案：**直接在已上线的生产环境进行实际测试，以缩短整改等待。

**评判结果：**作为主验收环境不可行；作为经过前置门禁的最终冒烟有条件可行。

| 维度 | 分析 |
| --- | --- |
| 技术可行性 | 使用现有服务最省环境准备，但无法安全、可重复地制造数据库提交失败、并发覆盖、验证码并发核销和进程中断 |
| 安全性 | 真实客户、资金、库存、短信额度、第三方账单均在影响范围内；1 分只限制单笔金额，不限制越权、重复副作用或信息泄漏 |
| 性能影响 | 竞争测试会持有真实行锁和连接池资源；回调失败演练会引发真实重试，影响正常结算 |
| 维护成本 | 部署前工作较少，异常后的对账、补偿、客户处理成本不可控；需要独立恢复记录，不能只靠代码回滚 |
| 兼容性 | Bearer 强制、旧 key 失效、JWT 撤销会影响存量客户端；共享数据库下新旧实例可相互覆盖状态 |

**结论与建议：**不把真实用户作为发现故障的测试样本。选择[方案三](PR219-03-紧急止血与临时隔离验证方案.md)；若必须立即线上动作，只做下一节的有限范围措施。

## 3. 可以立即做什么：止血而非故障实验

这些是待授权的运维/代码动作，本次没有执行。

1. 维护者确认实际线上提交及受影响入口。利用部署记录、现有日志与离线路由清单判断，不在线上对他人数据进行越权探测。
2. 无法立即安全修复的退款审核旁路、匿名资金写入或固定验证码恢复入口，暂时按完整路由集合关闭/限制；保留正常查询、浏览等无关功能。网关限制只是临时止血，最终仍须后端认证与归属校验。
3. 商家和用户归属不能只靠 IP 白名单判断；无完整权限实现时宁可明确暂停该操作。合法退款请求进入有权限、可审计的人工处理队列，处理前核对已有退款号及微信状态，不能从另一个入口再退一遍。
4. 暂停不安全的新业务请求时，**不要一刀切关闭微信回调和查单恢复**。在途支付/退款仍需可信接收与对账；接收失败必须保留可恢复记录，不能固定返回成功掩盖故障。
5. 将认证、当前用户作用域、管理员授权、权威价格等范围清晰的修复拆成最小补丁；先在隔离环境验证匿名/越权拒绝、合法本人请求、资产无意外变化，再发布。不能因为止血紧急而省略基本冒烟。
6. 向受影响用户显示真实维护状态；没有完整短信链路时不假装“验证码已发送”。管理员配置只在服务端维护。

若没有可用的网关开关或受控路由开关，不能假设配一个环境变量就能关闭功能；应实施明确的维护拒绝分支并验证其覆盖实际路由。

## 4. 生产小额冒烟的硬性前置条件

- [公共清单 U1—U8](PR219-04-逐项整改与验收清单.md)中对应本次开放功能的逻辑、数据库、故障恢复已通过；真实测试不是补这些证据的捷径。
- 内部测试用户、商户、商品、订单有服务端白名单；非白名单不能使用测试低价商品。**不能只在前端隐藏商品或把客户 SKU 临时改为 0.01 元。**
- 预算同时限制单笔、笔数、累计金额；退款额度与原单一致；暂停分销/积分等测试副作用必须是隔离的业务规则，不能篡改公共结算逻辑。若无法隔离，转方案二/三。
- 有负责人、操作员、对账人和停止权限；私钥/证书在受控运行环境，手机和付款账号得到授权。
- 回调域名、商户/AppID/子商户绑定正确；测试与真实订单路由不会交叉处理；后台任务不会重复处理同一笔交易。
- 发布前可确认迁移兼容性、数据库备份恢复能力及旧版本是否仍能理解新状态。数据库恢复不是撤销微信资金动作的工具。

## 5. 允许的操作顺序

1. 内部账号登录；查询本人订单/积分/券；检查预期 401/403 行为，但不尝试读取或修改真实第三方用户资源。
2. 通过真实服务端价格创建专用测试订单。产品允许时支付 1 分；验证微信与本地订单号、金额、状态一致。
3. 正常接收支付通知，查询确认本地账本和资产变化准确；不通过客户端返回页认定支付成功。
4. 使用已持久化的退款身份发起一次退款；查询真实终态，对比微信退款号、本地订单、账本、积分和券。退款受理不等于退款完成，到账也不承诺即时。
5. 真实短信仅向授权内部手机发送，完成找回及旧 token 撤销验证；不撞库、不压力轰炸、不测试别人的手机号。
6. 对账完成、未决项归零且监控正常，才考虑扩大开放范围。保留账务记录，不手工删掉测试单来让报表“干净”。

**禁止在生产做：**数据库 commit 故障注入、杀进程制造退款丢状态、重复或乱序攻击式重放、最后一件真实库存竞争、真实客户余额透支竞争、验证码猜测压力、未经授权的越权读取、未修复链路随机灰度。

1 分订单无法验证两次正金额部分退款，也无法验证普通金额分摊/舍入；这些应在隔离环境使用合成金额覆盖。需要真实部分退款时另批较小但足够的金额和笔数，不承诺所有商户都接受 1 分。

## 6. 停止、回退与恢复

任一项触发立即停止扩大开放：越权成功、旧 JWT 改密后仍有效、重复退款、金额不一致、退款/支付状态长期未知、资产重复变动、敏感日志泄漏。可用性指标与发布前基线比较，但**财务不变量异常容忍度为零**，不能被平均成功率掩盖。

- 先关闭有问题的新资金请求，保留可信回调、查单、对账处理能力。
- 代码回退只能回到仍保留安全止血的版本；不能为了可用性回退成匿名退款或固定验证码。
- 对已发出的退款，冻结其身份和参数，先查询再恢复；不换号、不能以“本地查不到”为由重复执行。
- 对未知的在途请求逐笔核实，记录操作人和审计事件。恢复数据库快照可能抹掉已发生的外部交易记录，不应在生产付款继续流入时直接整库回滚。

## 7. 前端与未完成项覆盖

本方案不会豁免任何项目。九条未完成项及六条前端影响逐项见[共用整改清单](PR219-04-逐项整改与验收清单.md)。其中 U3—U6 故障/竞争不得在生产首次证明；U1/U9 的真实服务联调可在本方案限定范围内执行。

前端需同步 Bearer、服务端管理员身份、本人作用域、401/403、权威价格与正整数数量、先发码后核销；旧客户端失效时给出明确迁移，不恢复旧安全旁路。

## 8. 官方依据与证据限度

- [微信申请退款](https://pay.weixin.qq.com/doc/v3/merchant/4013071036)：同一退款号只退一笔，失败重试必须沿用原号；受理不等于成功。支持先修幂等再做真钱验证，而非相反。
- [微信退款通知](https://pay.weixin.qq.com/doc/v3/merchant/4013071196)：重复通知可发生、失败会重试且仍需查询。不支持“正常 1 分跑通即覆盖失败恢复”。
- [AWS 幂等 API 实践](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)：请求身份与本地变更必须一致、重试不能额外产生副作用。
- [NIST SP 800-61 Rev.3，2025](https://csrc.nist.gov/pubs/sp/800/61/r3/final)：支持把应急响应与风险管理结合。这里的有限止血措施是结合 DS 的工程建议，不是 NIST 对 DS 的安全认证。
- 论文与“为什么故障注入不能由小额成功替代”的具体证据见[方案三的研究依据](PR219-03-紧急止血与临时隔离验证方案.md)。没有找到能证明直接对未修复电商生产系统做危险实验安全的论文，也不应据此声称存在。

## 9. 下一步操作

维护者选择是否发布最小止血补丁及是否批准最终内部小额冒烟；在此前仅执行离线整改和隔离验证。**本文件为方案交付，不构成生产变更授权，未执行部署、退款、发短信或故障测试。**
